# Acceptance Criteria

## 목적
이 문서는 MindSight 저장소 전역에서 공통으로 적용하는 구현/검증 기준을 명문화한다.  
기능 구현의 판단 기준은 `blueprint/`이며, 본 문서는 PR/리뷰/출시 전 점검 시 체크리스트로 사용한다.

## 적용 범위
- `apps/web`, `apps/api`, `packages/*`, `infra/*`, `scripts/*`, `docs/*`
- 사용자 화면(웹/모바일 반응형 기준)과 관리자 화면 모두 포함

## 전역 기준

### 1) Source Of Truth
- 기능 구현의 source of truth는 `blueprint/`다.
- 기존 코드/화면은 참고 자료로만 사용한다.
- 구현과 `blueprint`가 충돌하면 `blueprint`를 우선한다.

### 2) 충돌 처리 원칙
- `blueprint`와 구현이 충돌할 때 임의 판단으로 바로 덮어쓰지 않는다.
- 아래 항목을 문서화한 뒤 반영한다.
  - 어떤 blueprint 문서와 충돌하는지
  - 현재 구현 동작과 목표 동작
  - 차이 발생 원인
  - 영향 범위(기능/권한/보안/데이터)
  - 후속 조치

### 3) Production 문구 기준
- production 사용자 화면에 아래 성격의 문구를 남기지 않는다.
  - `preview`
  - `demo`
  - `showcase`
  - `developer note`
  - `helper`(개발 편의성 설명성 문구)
- 개발용 설명은 내부 문서(`docs/*`) 또는 개발 전용 경로에서만 허용한다.

### 4) 접근성(정보구조) 기준
- 핵심 사용자 기능은 메뉴 또는 하위 메뉴에서 접근 가능해야 한다.
- 최소 대상:
  - 체크인
  - 진단/설문
  - 챌린지
  - 일기
  - 활동로그
  - 상태/활동 대시보드
  - CBT
  - 요약리포트
  - 커뮤니티
  - 마이페이지

### 5) 디자인 변경 기준(현 단계)
- 현재 단계에서는 디자인 전면 수정/스타일 대수술을 진행하지 않는다.
- 우선순위는 기능 완결성과 정보구조 정합이다.
- 스타일 조정은 토큰/컴포넌트 체계를 깨지 않는 범위에서 최소 변경으로 수행한다.

### 6) Wireframe 부재 대응 기준
- wireframe이 없으므로 화면 완성도보다 다음을 먼저 맞춘다.
  - 기능 진입 경로
  - 상태 전이(로그인/온보딩/권한)
  - 도메인 간 연결(입력 → 대시보드/리포트)
  - 오류/빈 상태의 일관성

## 리뷰 체크리스트 (PR/통합 점검용)
- [ ] 변경 기능의 관련 `blueprint/<feature>/AGENTS.md` 및 `README.md`를 확인했다.
- [ ] 구현이 blueprint와 충돌하지 않는다.
- [ ] 충돌 항목이 있으면 차이/근거/영향/후속조치를 문서화했다.
- [ ] production 사용자 화면에 preview/demo/showcase/developer helper 문구가 없다.
- [ ] 핵심 기능이 메뉴/하위 메뉴에서 접근 가능하다.
- [ ] 디자인 대수술 없이 기능 완결성과 정보구조 우선으로 반영했다.
- [ ] 문서(`README`, `docs/*`, `.env.example`)와 구현이 일치한다.

## 증적(Evidence) 권장 형식
- 실행 명령: `install`, `lint`, `typecheck`, `test`, `build`, 실행 URL
- 화면 확인: 핵심 메뉴 접근 스크린샷 또는 경로 목록
- 충돌 문서: 충돌 항목별 링크

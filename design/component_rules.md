# Mindsight Component Rules

## 목적
이 문서는 Mindsight 서비스 전반에서 사용하는 공통 컴포넌트의 구조, 상태, 사용 규칙을 정의한다.  
목표는 화면마다 제각각 다른 UI를 만들지 않고, 디자인 시스템 기반의 일관된 구현을 유지하는 것이다.

---

## 1. 공통 원칙
- 같은 역할의 UI는 같은 컴포넌트를 사용한다.
- 새 컴포넌트를 만들기 전에 기존 컴포넌트 조합으로 해결 가능한지 먼저 확인한다.
- 모든 주요 컴포넌트는 최소 아래 상태를 가진다.
  - default
  - hover
  - focus
  - active
  - disabled
  - loading (필요 시)
  - error (필요 시)
- 모바일 우선으로 설계한다.
- 접근성(포커스, 명도 대비, aria)을 기본 포함한다.

---

## 2. 토큰 기반 구현 원칙

### 색상
모든 색상은 하드코딩하지 않고 토큰으로 사용한다.

권장 분류:
- `bg.*`
- `surface.*`
- `text.*`
- `brand.*`
- `accent.*`
- `status.*`
- `border.*`

### 간격
spacing scale을 사용한다.  
임의 값 남용 금지.

권장 예시:
- `space.1 = 4px`
- `space.2 = 8px`
- `space.3 = 12px`
- `space.4 = 16px`
- `space.5 = 20px`
- `space.6 = 24px`
- `space.8 = 32px`
- `space.10 = 40px`

### radius
권장 예시:
- `radius.sm = 10px`
- `radius.md = 14px`
- `radius.lg = 18px`
- `radius.xl = 24px`

### shadow
얕고 넓은 shadow만 사용한다.

권장 예시:
- `shadow.sm`
- `shadow.md`

---

## 3. Button

### 역할
사용자의 주요 액션 실행.

### variants
- `primary`
- `secondary`
- `soft`
- `tertiary`
- `danger`
- `ghost`

### sizes
- `sm`
- `md`
- `lg`

### 기본 규칙
- 가장 중요한 CTA 하나만 `primary`
- 보조 액션은 `secondary` 또는 `tertiary`
- 위험 액션만 `danger`
- 같은 구역에 primary 버튼 2개 이상 두지 않기
- 텍스트는 동사 중심

### 상태
- default
- hover
- focus
- disabled
- loading

### 스타일 방향
- radius: `radius.md` 이상
- 높이:
  - `sm`: 36px
  - `md`: 44px
  - `lg`: 48~52px
- primary는 `brand.primary`
- soft 버튼은 연한 보라/핑크 계열 배경

---

## 4. IconButton

### 역할
작은 보조 액션
예: 북마크, 좋아요, 닫기, 더보기

### 규칙
- `aria-label` 필수
- destructive action은 icon only 지양
- 피드 액션 버튼은 터치 영역 충분히 확보

---

## 5. Input

### 역할
짧은 텍스트 입력
예: 이메일, 닉네임, 검색

### 구성
- label
- input
- helper text
- error text

### 상태
- default
- focus
- error
- disabled
- success (선택)

### 스타일 방향
- 배경: soft surface, 파스텔 생상 그라데이션
- border: `border.soft`
- focus: `brand.primary` 계열
- radius: `radius.md`

### 규칙
- placeholder는 보조 힌트만
- label을 생략하지 않는다
- 에러 문구는 하단 고정 위치 사용

---

## 6. PasswordInput

### 역할
현재 비밀번호, 새 비밀번호, 비밀번호 확인 입력

### 추가 규칙
- show / hide toggle 제공
- 현재 비밀번호는 보안 설정에서만 요구
- 회원정보 일반 수정에는 비밀번호 입력을 강제하지 않는다

---

## 7. Textarea

### 역할
긴 글 입력
예: 일기, 게시글, 문의 내용

### 규칙
- 충분한 초기 높이 제공
- 글자 수 제한 시 counter 표시
- 목록/상세/작성 화면에서 역할을 명확히 구분
- 일기/문의는 작성 집중형 레이아웃 사용

---

## 8. Select / Dropdown

### 역할
고정 옵션 선택
예: 카테고리, 정렬, 필터

### 규칙
- 옵션 수가 적으면 segmented control/chips 우선 고려
- 모바일에서 터치하기 어렵지 않게
- placeholder는 선택 전 상태에서만 사용

---

## 9. SegmentedControl

### 역할
짧은 범주 전환
예: 7일 / 4주, 전체 / 일기 / 체크인

### 규칙
- 2~5개 옵션에 사용
- 선택 상태 명확히
- 배경은 soft surface, 선택 상태는 brand/soft accent 기반

---

## 10. Tabs

### 역할
상위 콘텐츠 구분
예: 피드 / 공지 / 북마크, 내 글 / 내 댓글

### 규칙
- 상위 수준의 구분에 사용
- 너무 많은 탭이면 필터/드롭다운 고려
- 모바일에서는 scrollable tabs 가능

---

## 11. Card

### 역할
정보 묶음의 기본 단위

### card types
- `summary_card`
- `content_card`
- `stat_card`
- `interactive_card`

### 스타일 방향
- 배경: `surface.base`
- radius: `radius.xl`
- shadow: 얕게
- border: 약하게

### 규칙
- 카드 안에 또 카드가 반복되지 않게
- padding은 충분히
- 클릭 가능한 카드인지 명확히

---

## 12. StatCard

### 역할
숫자/상태 요약
예: 대시보드 요약값, 활동 요약, 관리자 지표

### 구성
- title
- value
- delta 또는 보조설명
- optional icon

### 규칙
- 숫자가 가장 잘 보여야 함
- 색은 과도하게 쓰지 않음
- delta는 상승/하락 방향을 색과 텍스트 모두로 표시

---

## 13. FeedCard

### 역할
게시판 피드 표시

### 구성
- 고유번호
- 작성자/익명
- 작성 시각
- 제목(선택)
- 본문 미리보기
- 이미지 썸네일(선택)
- 액션: 좋아요 / 북마크 / 댓글 / 신고

### 규칙
- 본문 전체를 기본 노출하지 않음
- 긴 글은 미리보기 + 더보기
- 공지 카드는 일반 글과 배경/배지로 구분

---

## 14. JournalCard / JournalListItem

### 역할
일기 목록 표시

### 구성
- 제목(없으면 본문 일부)
- 작성일
- 수정일(선택)
- 미리보기 텍스트

### 규칙
- 본문 전체는 상세에서만
- 목록에서는 1~2줄 preview
- 자동 분석 결과는 기본 비노출

---

## 15. TicketListItem

### 역할
문의/피드백 티켓 목록 표시

### 구성
- 티켓번호
- 제목
- 유형
- 상태 배지
- 최근 업데이트 시각
- 재오픈 여부

### 규칙
- 상태를 가장 먼저 인지할 수 있어야 함
- 민감한 본문은 목록에서 최소 노출

---

## 16. ActivityLogDayItem

### 역할
하루 단위 활동 요약 표시

### 구성
- 날짜
- 체크인 여부
- 챌린지 여부/개수
- CBT 여부
- 일기 작성 여부
- 설문 여부

### 규칙
- 본문 전체 노출 금지
- 요약만 보여주고 상세는 원 기능으로 이동
- 활동로그는 확인/회고 중심

---

## 17. Badge / Tag / Chip

### 역할
짧은 상태/카테고리 표시

### 예시
- 답변 대기
- 진행 중
- 익명
- 설문 완료
- 위험 검토 필요

### 규칙
- 색상만으로 의미 전달하지 않기
- 상태 우선순위가 높은 것만 노출
- 너무 많이 나열하지 않기

---

## 18. App Shell / Navigation 규칙

### 목적
- 어느 화면에서든 핵심 기능으로 바로 이동할 수 있도록 전역 메뉴를 유지한다.

### 규칙
- `AppShell`은 상단 글로벌 메뉴를 기본 포함한다.
- 메뉴 항목(기본):
  - 홈
  - 체크인
  - 상태 대시보드
  - 활동 대시보드
  - 일기
  - CBT
  - 커뮤니티
  - 마이페이지
  - 관리자
- 현재 경로는 active 스타일로 즉시 구분한다.
- 모바일에서는 가로 스크롤 가능한 pill 메뉴를 사용한다.

## 18. Modal

### 역할
확인, 경고, 간단한 입력

### 사용 예
- 삭제 확인
- 차단 확인
- 신고 확인
- 제출 전 확인

### 규칙
- 긴 폼 전체를 넣지 않기
- 주요 행동과 취소를 명확히 분리
- 위험 액션은 `danger` 변형 사용

---

## 19. Drawer / BottomSheet

### 역할
필터, 정렬, 빠른 액션 메뉴

### 규칙
- 모바일에 적합
- 핵심 콘텐츠 전체 대체는 지양
- 닫기 경로 명확히

---

## 20. Toast / Snackbar

### 역할
짧은 성공/실패 피드백

### 규칙
- 짧고 명확한 문구
- 과도하게 연속 노출하지 않기
- 중요한 실패는 화면 내 에러와 병행

---

## 21. Banner / Alert

### 역할
계속 보여야 하는 안내
예: 이메일 인증 필요, 데이터 부족, 위험 안내

### variants
- info
- success
- warning
- danger

### 규칙
- 경고는 공포감 없이 명확하게
- dismissible 여부를 용도에 맞게 결정
- 이메일 미인증, 온보딩 미완료, 데이터 부족에 적극 활용

---

## 22. EmptyState

### 역할
데이터가 없을 때 다음 행동 제시

### 구성
- 제목
- 설명
- CTA

### 예시
- 아직 작성한 일기가 없어요
- 최근 7일 기록이 부족해요
- 저장한 북마크가 없어요

---

## 23. ErrorState

### 역할
로드 실패/제출 실패/권한 부족 안내

### 규칙
- “무엇이 문제인지” + “다음에 무엇을 하면 되는지” 포함
- 재시도 버튼 또는 돌아가기 버튼 제공
- 내부 에러 문자열 직접 노출 금지

---

## 24. Loading / Skeleton

### 역할
콘텐츠 로딩 중 화면 안정성 확보

### 규칙
- 리스트/카드/그래프 형태별 skeleton 제공
- 너무 화려한 shimmer 금지
- timeout/error fallback 고려

---

## 25. Chart Rules

### 공통 원칙
- 장식보다 해석 우선
- 색상만으로 의미를 전달하지 않음
- 축/라벨/요약 텍스트를 적절히 병행
- 결측 구간은 감추지 않음

### 상태 대시보드
- 우울/불안/불면은 같은 차트에 겹치지 않음
- 한 화면 안 세로로 분리 배치
- 7일 모드:
  - 기록 없는 날은 비우기
  - 기록 있는 점끼리 연결
- 4주 모드:
  - 해당 주에 데이터가 1개라도 있으면 주평균 생성
  - 주 전체 결측이면 빈 값
  - 값이 있는 주끼리 연결

### 활동 대시보드
- 캘린더는 “기록한 날” 중심
- 출석률이라는 표현보다 “기록한 날” 사용
- 최근 7일 CBT/챌린지/설문 카드 요약 우선

---

## 26. Layout Shell Rules

### App Shell
- 상단 헤더 또는 하단 내비 구조는 서비스 전체에서 일관 유지
- 사용자 화면은 넓은 single-column 중심
- 관리자 화면은 데이터 밀도 높게 가능하되 브랜드 톤 유지

### Section Spacing
- 섹션 간 간격을 일관되게 유지
- 카드 내부 padding은 충분히
- 한 화면에 2종류 이상의 spacing 체계를 섞지 않음

---

## 27. 폼 검증 규칙
- 필수/선택을 명확히 표시
- 실시간 검증은 최소화하되 중요한 오류는 즉시 보이게
- 에러는 입력 아래에 고정
- 전송 불가 사유를 설명 가능하게 표시

---

## 28. 접근성 규칙
- 모든 interactive element는 키보드 접근 가능
- 아이콘 버튼은 label 제공
- 에러는 색상만으로 표현하지 않음
- 그래프는 요약 텍스트 제공
- 포커스 상태를 시각적으로 명확히 표시
- 작은 터치 영역 금지

---

## 29. 관리자 전용 규칙
- 일반 사용자용 UI보다 정보 밀도 높아도 됨
- IP는 기본 사용자 목록에 비노출
- 차단/보안 조치 상세 화면에서만 제한적 노출
- 큐는 목적별로 분리
  - moderation
  - support
  - safety
  - ops
  - ml

---

## 30. 금지 패턴
- 같은 역할의 컴포넌트를 화면마다 다르게 구현
- 버튼/카드/입력 규칙을 기능마다 다르게 사용
- 게시글/일기/문의 본문을 목록에서 전부 노출
- 관리자 화면을 브랜드와 완전히 다른 스타일로 구성
- 정보량 많은 화면을 여백 없이 채우는 것

---

## 31. 새 컴포넌트 추가 규칙
새 컴포넌트를 만들기 전에:
1. 기존 컴포넌트 조합으로 해결 가능한가
2. 여러 화면에서 재사용되는가
3. 상태 정의가 충분한가
4. 토큰 기반으로 구현 가능한가

새로 만들면 아래를 문서화한다.
- 목적
- props
- states
- variants
- 사용 예시
- 금지 패턴

## 33. 최종 기준 문장
Mindsight의 컴포넌트는  
**“부드러운 표면 위에 정돈된 정보 구조를 얹고, 사용자가 예민한 상태에서도 예측 가능하게 상호작용할 수 있도록 만든다”**  
를 기준으로 구현한다.
